# Git и рабочее дерево задачи

Работайте по [§ 9 спецификации OWL](../../docs/owl_spec.md#9-параллельная-работа-и-worktree). Учёт назначения и статусов ведётся по [инструкции `owl-tasks`](../owl-tasks/SKILL.md): Git-состояние само по себе не меняет статус. Этот скил не предоставляет разрешения на публикацию, очистку или запись в чужое дерево и не заменяет проверку результата задачи.

1. **Определите пути и полномочия.** Получите корень основного дерева проекта, абсолютные пути к общей `tasks/ROADMAP.md`, папке назначенной задачи и её предполагаемому `worktree/`, целевую ветку интеграции, ID, исполнителя и разрешённые Git-операции. Не вычисляйте путь к очереди относительно worktree: `tasks/` обычно игнорируется Git и находится вне него. Проверьте назначение и зависимости в общей очереди с координатором; исполнитель меняет только своё дерево и записи задачи, изменения очереди передаёт координатору. Перед каждым существенным шагом следуйте `AGENTS.md` текущего рабочего дерева: прочитайте `rules/index.md`, базовые и применимые правила и передавайте первоисточники по его инструкции. При недоступности обязательных входов остановите соответствующий шаг и сообщите, чего не хватает.
2. **Проверьте исходное состояние до создания.** Установите фактические корни и ветки через `git rev-parse --show-toplevel`, `git status --short --branch`, `git worktree list --porcelain`; проверьте незакоммиченные и неотслеживаемые файлы во всех затрагиваемых деревьях. Убедитесь, что для задачи ещё нет дерева и ветки, а каталог назначения не содержит чужих данных; наличие незнакомых файлов — повод выяснить происхождение, не удалять их. Выберите конкретный коммит целевой исходной ветки и проверьте, что в нём уже есть необходимые требования, правила и конфигурация (например, `git show <commit>:AGENTS.md` и нужные файлы). Незакоммиченные изменения основного дерева не попадут в новую ветку автоматически: не копируйте их молча, не переключайте занятую ветку и не используйте `reset`, `clean`, `stash` или принудительное создание для обхода конфликта. При недостаточной исходной ревизии сначала согласуйте, как получить пригодную ревизию, сохраняя локальные данные.
3. **Создайте один worktree.** Если проверки прошли и нет существующего дерева задачи, из выбранного коммита выполните `git worktree add -b <ветка-задачи> <папка-задачи>/worktree <исходный-коммит>`; имена и пути подбирайте для данного проекта, не переписывая существующую ветку. Проверьте `git worktree list --porcelain`, ветку, HEAD и `git status` нового дерева. Запишите реальный путь, ветку и исходный коммит в рабочую запись `task.md`; передайте исполнителю абсолютные пути к дереву, папке задачи и общей очереди. Работу с проектом и проверки выполняйте в новом дереве, записи — рядом с ним. Проверьте оттуда доступность инструкций и применимых правил, а также скилов; если OpenCode не обнаруживает проектные скилы за границей worktree или для внешней папки задач требуется разрешение, сообщите об этом и запросите доступ по политике среды, не объявляя интеграцию работающей. Для параллельных задач учитывайте общие ресурсы и пересекающиеся контракты по правилам проекта.
4. **Продолжите существующую задачу без повторного создания.** Заново прочитайте очередь, `task.md` и применимые правила; проверьте `git worktree list --porcelain`, `git branch -v`, `git status --short --branch` в найденном дереве и целевой ветке, HEAD, незакоммиченные и неотслеживаемые файлы и историю относительно исходного коммита. Сверьте путь, назначение и сделанные ранее проверки с фактическим состоянием, включая изменения требований после создания ветки. Если дерево или ветка отсутствует, перемещена либо занята другой сессией, выясните судьбу прежней работы и владение до восстановления; не создавайте второй экземпляр и не делайте `prune` или `repair` вслепую. Запишите следующий шаг и недостоверные прежние проверки в рабочую запись.
5. **Интегрируйте только принятый результат.** Получите подтверждение актуальности ревью и обязательных проверок именно интегрируемого изменения; отдельно проверьте разрешения на commit, push, PR и merge по правилам проекта и среды. Сверьте текущее состояние целевой ветки (при необходимости получите свежие сведения с удалённого репозитория), разницу и общую базу веток, отсутствие чужих незакоммиченных изменений в дереве интеграции. Если целевая ветка продвинулась, проверьте совместимость и повторите затронутые проверки на объединённом результате; конфликт или неизвестное состояние — остановка и согласование, а не принудительная перезапись. Фиксируйте только проверенные файлы задачи; не используйте `--force` для push/merge. После разрешённой интеграции проверьте итоговую ревизию, состояние целевого дерева и требуемые проверки сочетания изменений, затем передайте координатору свидетельства для `done`. Отправленная ветка или успешное ревью без интеграции не означают `done`.
6. **Очищайте только по отдельному разрешению.** После принятой интеграции и проверки локальных данных можно удалить дерево штатным `git worktree remove <путь>`; проверьте состояние и не применяйте `--force` к дереву с незавершёнными файлами. Удаление ветки, локальных записей задачи и удалённой ветки — отдельные действия по политике проекта; сохраните постановку и отчёты. Если разрешения на очистку нет, оставьте дерево на месте и сообщите его путь.

При передаче результата различайте подготовку, проверку, интеграцию и публикацию: назовите проверенные ревизии, команды и их результаты, сохранённые локальные изменения, ограничения среды и следующий шаг. Отсутствующую проверку не называйте пройденной.
