# Проба 024: перенос, восстановление и параллельная работа

**Результат задачи 024:** описанные ниже сценарии пройдены в указанных границах; это не приёмка всего MVP. Требования — [§§ 5, 8–9, 13 спецификации](owl_spec.md#13-критерии-готовности-mvp), постановка — локальный `.owl/tasks/task_024/task.md` основного дерева. Для разработки OWL прочитаны `AGENTS.md`, `rules/index.md`, `rules/development.md`, `rules/verification.md`, §§ 5, 8–9, 13 спецификации, §§ 8, 10, 14 [принципов](ai_development_principles.md), [схема develop](../workflows/develop.md), инструкции `owl-orchestrator`, `owl-tasks`, `owl-git`, `owl-init` и [профиль OKF](../skills/owl-okf/references/okf_profile.md). Для временных проектов читались их `AGENTS.md`, `rules/index.md`, `rules/base.md`, при оценке CLI — `rules/cli.md` и `docs/counter_spec.md`.

## Условия и перенос правил

- 3 октября 2026, OpenCode `1.18.33`, исходное дерево отчёта OWL — `033e06f6c6239af41dcbdde92269c3e14dc91989`. Два отдельных временных Git-проекта `/tmp/opencode/owl-024-a` и `/tmp/opencode/owl-024-b` созданы `git clone --local` от принятой пробы 023 (`5b76ad7b536c577b59b1bebdd6ab1afb55f729b7`); установленный в ней пакет OWL происходит из `c4ab825626cd492c74553501e9d850cfe88ed7ce`. Это две копии **ранее установленного** OWL, а не новая проверка установки. SHA-256 установленного `owl-orchestrator/SKILL.md` в обоих проектах — `e5a4dcb73b34124d9fba946b0daead20b4efee27257fcafc54e703a57e86ed86`; `owl-git/SKILL.md` — `b57d4062d451b8180936af6ce75746c80e0d65d602f75033a68e8ae5b1d5f1d8`.
- A на `9730952` дополнил индекс собственным `rules/cli.md` (ровно `2\n` без префикса); B на `7ae82ab` получил другое базовое и CLI-правило (`B:`). В первой **реальной** read-only сессии `opencode run --pure --model openai/gpt-6-sol` в A скил загрузился, агент прочитал `AGENTS.md` → индекс → оба правила и спецификацию, назвал точные stdout `2\n`, пустой stderr и отсутствие префикса. В первой сессии B он прочитал его же локальный маршрут и **остановил переход**, поскольку старое `docs/counter_spec.md` всё ещё требовало `2\n` вопреки новому правилу `B:`. Конфликт не был принят как успех.
- После согласования спецификации B (`8a46142`, ожидается `B:2\n`) второй реальный вызов в B выбрал B-правила и спецификацию, указал, что прежний код/прошедшие старые тесты печатают `2\n` и **не** подтверждают новое требование. Агент прямо отверг перенос A-правила в B. Код B в этой задаче не исправлялся: это проверка выбора правил и диагностики, а не реализации новой CLI-функции.

## Восстановление, независимые задачи и зависимость

В A координатор один раз создал локальную игнорируемую Git `.owl/tasks/ROADMAP.md` и три постановки: 101 и 102 назначены OpenCode без зависимостей, 103 зависит от обеих. В очереди основного дерева изначально `101/102: in_progress`, `103: planned`; в отдельных деревьях очередь не создавалась. Перед созданием деревьев проверены Git-ветки и статус; исходная ревизия `9730952` содержала инструкции и правила.

| Наблюдение | Проверка и результат |
|---|---|
| Изоляция 101/102 | `git worktree add -b owl/task-101 .owl/worktree/101 HEAD` и отдельно `owl/task-102` от `9730952`. 101 добавил только `square.py`, `tests/test_square.py`; 102 — только `cube.py`, `tests/test_cube.py`. В каждом дереве `python -m unittest discover -s tests`: 3 OK; `git status` показывал только свои два новых файла. Git `check-ignore .owl/tasks/ROADMAP.md` подтвердил игнорирование единой очереди. Работа велась в двух деревьях с **последовательными действиями одного испытателя**, без параллельных сессий-исполнителей и без претензии на атомарную блокировку. |

Локальная очередь и рабочие записи не синхронизируются Git. Проверены действительные Git-ветки и деревья, а не наличие каталогов с похожими именами.

## Отрицательные входы и ограничения

| Вход | Наблюдавшийся отказ |
|---|---|
| Обязательное правило отсутствует | В B временно добавлена ссылка на `rules/missing-audit.md` в индекс как обязательная для CLI. Реальный `opencode run --pure` получил `File not found` при чтении и явно сообщил, что проверку нельзя принять. Ссылка удалена, `git status` B снова чистый. |
| Обязательная проверка недоступна | Read-only вызов B запустил требуемую для пробы `python -m owl_missing_required_check`: `No module named owl_missing_required_check`, exit 1; агент отказался назвать её успешной. Это инъекция отсутствующего инструмента, а не штатная команда проекта (его действительная команда тестов — `python -m unittest discover -s tests`). |
| Модель недоступна | `opencode models openai/owl-missing-model` → `Provider not found: openai/owl-missing-model`. `opencode run --pure --model openai/owl-missing-model` вернул ошибку `UnknownError`/`Unexpected server error` вместо ответа модели. Следовательно, шаг на этой модели **не выполнен**; диагностическое сообщение самой команды запуска не называет недостающую модель точно. Это ограничение диагностики среды, не подтверждение корректного перехода OWL при отсутствующей модели. Реальные успешные агентские вызовы выше шли на `openai/gpt-6-sol`; другой уровень модели в пробе 024 не запускался. |
| Разрешение на чтение отсутствует | Отдельный read-only запуск в A с временной **только для процесса** переменной `OPENCODE_CONFIG_CONTENT='{"permission":{"external_directory":"deny"}}'` запросил обязательный внешний файл B. Tool `Read` отказал по `external_directory`; агент назвал отказ, не объявил правило проверенным и потребовал доступ к нужному пути. Без этого ограничения отдельный вызов действительно читал тот же внешний файл, так что проба проверяет различие разрешений, а не отсутствие файла. Глобальные настройки и проектные файлы конфигурации не менялись. |
| Публикация запрещена политикой | В read-only запросе B было **задано условие** запрета commit/merge до разрешения владельца; загрузив `owl-git` и `owl-tasks`, агент отказался считать `done` до разрешённой интеграции и проверки результата. Это проверка решения при смоделированном запрете, не наблюдавшийся отказ реального Git-права. |

Не проверены одновременная запись двумя процессами, перенос локальной очереди между машинами, удалённая публикация временных проектов и успешное выполнение B-реализации под её новым требованием. Проба подтверждает режим одного редактора и последовательной интеграции **в пределах этих условий**, но не распределённое владение. Повторной проверкой являются приведённые результаты команд на точных ревизиях; наличие записей/скилов само по себе не принималось как результат.
