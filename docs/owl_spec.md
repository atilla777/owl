# OWL — верхнеуровневая спецификация

**Версия документа:** 0.1.  
**Назначение:** определить целевое поведение OWL и границы первого MVP. Детальные инструкции скилов, схемы workflow и шаблоны разрабатываются последовательно в отдельных задачах.  
**Важно:** этот документ описывает требуемый результат, а не утверждает, что перечисленные возможности уже реализованы. Первой сессии посвящён отдельный документ `owl_start_prompt.md`.

## 1. Назначение и цель

OWL — набор переиспользуемых Agent Skills, справочных инструкций, Markdown-шаблонов и текстовой конфигурации для AI-сред разработки (harness), прежде всего OpenCode.

OWL помогает согласовывать требования, планировать и выполнять небольшие задачи, получать проверяемые результаты, сохранять рабочее состояние и использовать несколько изолированных рабочих деревьев Git. Основа подхода — документ «Принципы организации разработки с AI-агентами».[^principles]

**Главный результат OWL — не прохождение формальных этапов, а изменение, соответствующее согласованным требованиям и подкреплённое достаточными проверками.** Объём процесса должен соответствовать сложности и риску задачи.

OWL не содержит собственных скриптов, CLI, серверов, баз данных, плагинов, программных валидаторов или исполнителя workflow. Работа выполняется агентами по инструкциям с использованием существующих инструментов harness, Git и целевого проекта. Текстовые определения команд и профилей агентов допустимы. Это ограничение относится к устройству OWL, а не запрещает разработку программного кода в целевых проектах.

OWL предписывает правила, но не гарантирует техническую невозможность их нарушить. Обязательные программные ограничения, права доступа и автоматические проверки обеспечиваются доступными средствами среды и проекта. Нельзя выдавать наличие инструкции за независимый механизм контроля.

## 2. Область применения и границы MVP

Скилы должны подходить для разных проектов без переписывания их общих инструкций. В них не зашиваются конкретный язык, движок, архитектура приложения, тестовый раннер или критерии ревью отдельного проекта.

В MVP реализуется и проверяется интеграция с одной выбранной версией OpenCode. Переносимость содержания на другие harness закладывается с начала; работоспособность интеграций с Codex, Claude Code и другими средами не объявляется без отдельной проверки. Формат Agent Skills допускает пакет из `SKILL.md` и дополнительных материалов без скриптов.[^skills-format]

MVP должен поддерживать:

- установку инструкций в новый или существующий проект, не повреждая его материалы;
- обсуждение требований, подготовку задач, выполнение и диагностику проблем;
- общий учёт задач, рабочие артефакты и продолжение после прерывания;
- workflow с условиями перехода на основании пригодных артефактов;
- выбор применимых правил проекта и передачу достаточного контекста;
- отдельный worktree для каждой выполняемой задачи и параллельную работу над назначенными задачами;
- два уровня моделей, проверку результатов и отдельно запускаемый анализ процесса.

**Не входят в MVP:** собственная программная инфраструктура, автоматическая синхронизация локальных задач между компьютерами, конкурентный автономный захват задач несколькими координаторами, универсальный язык workflow, обязательная полная трассировка сессий, автоматическое самоизменение скилов и публикация без разрешения. Полноценное обновление между версиями OWL может быть добавлено после безопасной первоначальной установки.

## 3. Разделение общей и проектной информации

| Где находится информация | За что она отвечает |
|---|---|
| Скилы OWL и общие справочники | Как выполнить типовую работу, проверить входы, передать результат и действовать при проблеме |
| `rules/` целевого проекта | Как работать именно в этом проекте: стиль, архитектурные ограничения, проверки, ревью, безопасность, Git-политика, особенности среды |
| `docs/` целевого проекта | Как система должна себя вести; существенные принятые решения и их основания |
| `tasks/` целевого проекта | Какие изменения выполняются, их состояние, зависимости и рабочие свидетельства |
| Конфигурация harness | Конкретные модели, профили агентов, разрешения, команды и возможности делегирования |
| `AGENTS.md` целевого проекта | Короткая точка входа, базовые ограничения и маршруты к перечисленным источникам |

«Проектная специфика находится в rules» означает специфику **процесса разработки**. Функциональные требования не переносятся из `docs/` в правила, а идентификаторы моделей — из конфигурации harness в текст каждого скила.

Описание архитектурного решения и причины выбора сохраняются в ADR. Обязательные ограничения для дальнейших изменений могут быть отражены в правилах со ссылкой на ADR, без независимого переписывания самого решения.

Для каждого факта должен существовать один канонический источник. Индексы, планы и передачи контекста ссылаются на него, а не создают альтернативную версию требований или состояния.

## 4. Спецификации и архитектурные решения

`docs/` — нормативный источник истины: код должен соответствовать согласованному поведению независимо от того, реализовано оно уже или только запланировано. Степень реализации отражается задачами, а не подменяет смысл спецификации.

`owl-brief` фиксирует согласованные требования до реализации. Предварительные идеи и открытые вопросы явно отделяются от принятых требований. При изменении существующего поведения обновляются соответствующие спецификации и затронутые задачи.

Задача задаёт конкретное приращение и критерии его приёмки. Ревью проверяет это приращение и отсутствие регрессий, но не требует за одну задачу реализовать все ещё невыполненные требования доменной спецификации. При этом решение не должно противоречить уже согласованным требованиям к следующим приращениям.

ADR создаётся только для существенного решения, а не автоматически для каждой фичи. Один ADR описывает одно решение; при его замене сохраняются история и ссылка на новое решение. Не нужно вести единственный переписываемый «ADR всей фичи».

Документирование отражает согласованные решения. Обнаружив расхождение требований и реализации, агент должен инициировать исправление или пересмотр решения, а не молча подогнать спецификацию под код.

Если требования или правила меняются во время работы, пересматриваются затронутые задачи, планы и результаты проверок. Перезапускать незатронутые шаги не требуется.

## 5. Поиск и загрузка правил проекта

### 5.1. Базовый механизм

Используется единый маршрут:

```text
AGENTS.md → rules/index.md → применимые документы и необходимые ссылки
```

`AGENTS.md` каждого целевого проекта содержит явную инструкцию пользоваться этим маршрутом перед выполнением шага, а не только ссылку на каталог. Это существенно для OpenCode: ссылки в `AGENTS.md` сами по себе не означают автоматической загрузки содержимого; документация предусматривает явные инструкции агенту читать нужные файлы.[^opencode-rules]

В MVP не создаются отдельный скил поиска правил, поисковая база или механизм автоматического исполнения тегов. Шаблон подключения `AGENTS.md` задаёт общий порядок выбора правил и передачи контекста; `owl-init` создаёт по нему точку входа нового проекта либо сохраняет существующий `AGENTS.md` и дополняет его необходимыми указаниями без дублирования. После подключения инструкции доступны всем агентам и скилам из `AGENTS.md` проекта: отдельный распространяемый справочник выбора правил не требуется. Собственный `AGENTS.md` репозитория OWL описывает тот же порядок для работы над OWL, но не используется как шаблон для других проектов. Пути `rules/` и `docs/` разрешаются относительно рабочего дерева целевого проекта, а не каталога установленного скила. Путь к общей папке задач передаётся отдельно.

### 5.2. Индекс правил

`rules/index.md` — компактный навигатор. Каждая запись содержит ссылку, краткое назначение и условие чтения: этап работы, затрагиваемую область или характер риска. Небольшая группа базовых правил читается всегда; остальные выбираются по задаче.

Пример организации, а не обязательный набор файлов:

```markdown
# Базовые правила

- [Общие ограничения](base.md) — читать всегда.

# Проектирование и реализация

- [Архитектура](architecture.md) — plan, implement, review:
  при изменении границ компонентов, зависимостей или публичных контрактов.
- [Стиль кода](coding.md) — implement, review: при изменении кода.

# Проверка результата

- [Проверки](verification.md) — plan, implement, review, git, fix:
  выбрать команды и способы наблюдения результата.
- [Особенности ревью](review.md) — review: читать для каждого ревью.
- [Интерфейс](ui.md) — plan, implement, review:
  при изменении видимого поведения или взаимодействия пользователя.
```

Названия этапов соотносятся с ролями скилов. Условия могут учитывать пути, домен, тип изменения и риск; совпадение имени файла не является единственным критерием применимости.

Теги OKF допустимы как дополнительная тематическая классификация. Они не обязательны для маршрутизации и не заменяют индекс. Не нужно одновременно поддерживать две независимые карты «шаг → правила» в индексе и в тегах каждого файла.

### 5.3. Обязательное поведение агента

Перед существенными действиями агент следует инструкциям `AGENTS.md` своего проекта: определяет текущий шаг и область задачи, читает индекс и базовые правила, затем открывает применимые документы. При расширении области изменения набор правил пересматривается.

Правила реализации должны быть доступны и ревьюеру, когда он проверяет их соблюдение. Нельзя ограничивать ревью только документами с меткой `review` и исключать применимые архитектурные или предметные ограничения.

При передаче субагенту передаются ссылки на найденные правила и основания их применимости. Субагент читает первоисточники и при необходимости дополняет набор; резюме основного агента не заменяет правила. Для существенных шагов список реально использованных правил кратко указывается в плане или соответствующем отчёте, без отдельного обязательного файла контекста.

Если обязательный документ недоступен либо существенные правила противоречат друг другу, агент сообщает о проблеме. Он не выдумывает недостающее правило и не объявляет собственное исключение. Рекомендации отделяются от обязательных требований; локальные правила не могут расширять полномочия, заданные средой. Противоречие нельзя разрешать принципом «последний прочитанный текст важнее».

Добавление или перемещение правила сопровождается обновлением индекса. Маршруты чтения поддерживаются в индексе; конкретные требования — в самих документах.

## 6. Скилы, агенты и пользовательские сценарии

Скил — инструкция, а не отдельный агент или процесс. Основной агент может использовать несколько скилов последовательно. В OpenCode скилы загружаются по необходимости; конфигурация агентов и их делегирование — отдельные механизмы.[^opencode-skills]

### 6.1. Пользовательские точки входа

| Команда | Ожидаемое поведение |
|---|---|
| `/owl-brief <запрос>` | Уточнить и согласовать требования, обновить спецификации, подготовить задачи. Не начинать реализацию автоматически |
| `/owl <ID>` | Выполнить или продолжить конкретную назначенную задачу |
| `/owl` | В координирующей сессии продолжить подходящую незавершённую задачу либо выбрать первую готовую. Один вызов — одна задача, не вся очередь |
| `/owl-fix <проблема>` | Исследовать симптом, проверить причину, подготовить исправление и при допустимости выполнить его через общий цикл |

В рабочей сессии, уже привязанной к задаче, `/owl` продолжает именно её и не захватывает новую. Если задача недоступна для выполнения, команда объясняет причину. Установка и self-review доступны как служебные операции; отдельные slash-команды для каждого внутреннего шага не обязательны.

### 6.2. Состав и ответственность

| Скил | Ответственность и граница |
|---|---|
| `owl-init` | Установить и подключить OWL, сохранить существующие настройки, определить необходимые настройки проекта. Не исполнять задачи разработки вместо оркестратора |
| `owl-brief` | Согласовать «что и зачем», определить границы и приёмку, декомпозировать работу. Не писать подробный технический план каждой будущей задачи |
| `owl-orchestrator` | Провести конкретную задачу через workflow: проверить входы, выполнить либо делегировать шаг, принять результат, организовать возвраты и завершение |
| `owl-plan` | Изучить существующее решение и подготовить технический подход, шаги и проверки одной задачи |
| `owl-implement` | Реализовать изменение и тесты, выполнить проверки, устранить замечания в рамках задачи. Не менять требования ради удобства реализации |
| `owl-review` | Проверить изменение относительно требований, правил и фактических свидетельств. Отделить дефекты, риски и предложения; по умолчанию не исправлять проверяемое изменение самому |
| `owl-document` | Отразить согласованные требования и решения в спецификациях, ADR и связанных материалах. Не принимать продуктовые или архитектурные решения вместо ответственных |
| `owl-fix` | Воспроизвести проблему либо обозначить ограничения, исследовать причины, сформировать исправление. Использовать общий цикл выполнения, а не собственную копию реализации и ревью |
| `owl-tasks` | Создавать и сопровождать задачи, порядок, зависимости, назначения, состояния и расположение артефактов. Не оценивать самостоятельно качество технического решения |
| `owl-git` | Организовать безопасную работу с ветками и worktree, проверку Git-состояния, интеграцию и очистку. Следовать разрешениям проекта; `gh` не обязателен |
| `owl-okf` | Поддерживать профиль OKF для правил и документации: оформление, ссылки, индексы, операции сопровождения. Не дублировать принятие решений и управление workflow |
| `owl-self-review` | Анализировать доступные свидетельства выполнения задач и предлагать улучшения процесса. Не переписывать OWL автоматически |

Имя `owl-orchestrator` сохраняется; пользовательская команда — `/owl`. Отдельный «оркестратор над оркестраторами» не создаётся.

`owl-brief`, `owl-fix` и `owl-orchestrator` — разные управляющие сценарии одного основного агента, а не три обязательных слоя делегирования. После диагностики `owl-fix` передаёт конкретную задачу в общий цикл в том же управляющем контексте. Исправление замечания текущей задачи обычно возвращается в `owl-implement`, а не запускает новый пользовательский сценарий целиком.

Документирование может понадобиться при brief, планировании или реализации. Оно не является обязательной церемонией в конце каждой задачи. Существенные изменения документов входят в ревью общего результата.

## 7. Workflow на основании артефактов

### 7.1. Контракт шага

Для каждого шага схема workflow определяет:

1. Входные артефакты и условия их пригодности.
2. Работу и ответственный скил.
3. Предпочтительный контекст выполнения и уровень модели.
4. Выходные артефакты и критерии успешного завершения.
5. Допустимые возвраты, блокировки и условия остановки.

Артефактом может быть файл, раздел документа, изменение кода или результат проверки. Он может поступать от любого предшествующего шага либо из уже существующей документации проекта.

**Наличие файла — необходимое условие там, где файл требуется, но не доказательство готовности.** Проверяются содержательность, принадлежность задаче, актуальность, результат и отсутствие блокирующих вопросов. Пустой шаблон не считается завершённым артефактом.

Каноническая последовательность и условия переходов хранятся в схеме workflow. Скилы описывают выполнение своих операций и не поддерживают независимо переписанные копии полного процесса. Схема — обычный документ, читаемый агентом; собственный интерпретатор не нужен.

### 7.2. Базовый цикл

| Шаг | Основания для начала | Требуемый результат |
|---|---|---|
| Подготовка | Готовая назначенная задача и завершённые зависимости | Известные пути задачи и worktree, доступные инструкции и среда |
| Планирование | Постановка, приёмка, спецификации и применимые правила | Достаточный технический план и способы проверки |
| Реализация | Пригодный актуальный план | Изменение, тесты и фактические результаты проверок |
| Документирование, при необходимости | Согласованные требования или решения | Соответствующие изменения документации |
| Ревью | Проверяемая версия изменения, требования и результаты проверок | Отчёт с замечаниями, ограничениями и выводом о готовности |
| Исправления, при необходимости | Обоснованные замечания | Исправленное изменение, повторные затронутые проверки и ревью |
| Интеграция | Актуальное принятое ревью и успешные обязательные проверки | Интегрированное изменение и проверка объединённого состояния |

Для небольшого исправления допускается краткий план в постановке. Облегчённый вариант должен быть предусмотрен workflow; нельзя произвольно объявлять обязательный артефакт ненужным. Feature и fix используют общую основу, различаясь подготовкой и соразмерной глубиной, а не дублированием всего процесса.

### 7.3. Достоверность и актуальность

Результаты проверок и ревью связываются с проверенной ревизией или однозначно определённым состоянием изменения. Пока проводится итоговое ревью, проверяемое изменение не должно одновременно изменяться другим исполнителем.

После изменения кода, требований или правил оркестратор определяет, какие прежние результаты больше не подтверждают готовность. Повторяются затронутые проверки; сам факт существования старого отчёта не разрешает интеграцию.

Для ревью допустимы известные неуспешные результаты тестов: оно может помочь исследованию. Для приёмки обязательные проверки должны быть успешны. Пропущенная или недоступная проверка не считается пройденной; изменение требований к приёмке требует явного согласования.

Недостающий результат получают выполнением работы, а не написанием отчёта о якобы выполненной работе. При противоречивых входах, отсутствии доступа или повторяющихся безрезультатных попытках сохраняются причина, сделанное и следующий разумный шаг. Предел повторных попыток и порядок эскалации задаются явно, без бесконечного автономного цикла.

## 8. Учёт задач и локальные артефакты

### 8.1. Структура целевого проекта

```text
project/
  AGENTS.md
  .gitignore
  docs/
    index.md
    <домен>_spec.md
    adr/
      <номер>-<решение>.md
  rules/
    index.md
    ...правила проекта...
  tasks/                           # Не отслеживается основным Git worktree
    ROADMAP.md                     # Единый оперативный учёт
    task_001/
      task.md
      plan.md                      # Когда требуется отдельный план
      review.md                    # Результат ревью
      worktree/                    # Код и документы отдельной ветки задачи
    task_002/
      ...
```

Расположение `tasks/` игнорируется основным рабочим деревом. Код внутри зарегистрированного worktree остаётся под управлением Git своей ветки. Не создаётся собственная копия ROADMAP внутри каждого worktree.

`tasks/` локален: его содержимое не переносится и не резервируется автоматически через Git. Долговременные знания, существенные решения и правила должны попадать в отслеживаемые документы; единственная важная копия знания не должна навсегда оставаться в локальном отчёте.

### 8.2. Источники состояния

`tasks/ROADMAP.md` содержит ID, краткое название, тип, порядок, статус, зависимости и назначенного исполнителя. Порядок задаётся расположением записей; ID не меняется при перестановке. Зависимости хранятся в одном направлении — «зависит от»; обратные списки не дублируются.

`task.md` содержит подробную постановку, приёмку, ссылки на спецификации, расположение worktree и ветки, рабочую запись и итог. Статус задачи не дублируется как второй авторитетный источник. Рабочая запись должна позволять продолжить после прерывания: что изменено, что проверено, что осталось и почему работа остановилась.

Технический подход и план реализации — один артефакт `plan.md`, а не два обязательных документа с повторяющимся содержимым. Результаты проверок и завершения можно хранить в `task.md`; отдельный файл для каждого действия не требуется.

### 8.3. Жизненный цикл

Основные состояния: `planned`, `in_progress`, `ready_to_merge`, `done`, `blocked`.

- `planned` — согласованная задача; она доступна для выбора после выполнения зависимостей и подготовки достаточной постановки.
- `in_progress` — назначена и выполняется. Внутренний шаг определяется по рабочей записи и пригодным артефактам.
- `ready_to_merge` — результат проверен в своей ветке и готов к интеграции.
- `done` — изменение интегрировано в целевую ветку и предусмотренные проверки объединённого результата выполнены.
- `blocked` — есть конкретное препятствие, требующее действия или решения; причина и условия продолжения записаны.

Ожидание ещё не выполненной зависимости само по себе не требует `blocked`. Зависимость снимается после `done`, а не только после готовности к merge. Для согласованной исследовательской задачи без изменения репозитория завершение означает принятый исследовательский результат; фиктивный коммит не нужен.

## 9. Параллельная работа и worktree

Каждая исполняемая задача, изменяющая проект, получает отдельную ветку и worktree. Удобное соглашение MVP — `tasks/task_<ID>/worktree/`. Артефакты задачи находятся рядом, а не внутри рабочего дерева.

Агенту явно передаются корень рабочего дерева, папка задачи и расположение общей очереди. Изменения кода, документов и проверки выполняются в worktree; записи задачи — в её папке. Нельзя полагаться на неизменность текущей директории между действиями.

При возобновлении проверяются существующие ветка, worktree и незавершённые изменения. Нельзя создавать вторую рабочую копию той же задачи или уничтожать первую ради повторного запуска.

Рабочее дерево создаётся из определённого Git-состояния, а не как копия незакоммиченной основной директории.[^git-worktree] До начала задачи в исходной ревизии должны быть доступны необходимые спецификации, правила и установленная конфигурация. Появившиеся позже изменения требований должны быть явно учтены.

### 9.1. Координация без сервера и блокировок

В MVP действует режим **«несколько исполнителей, один редактор общей очереди, последовательная интеграция»**. Координирующая сессия назначает задачи и изменяет ROADMAP через инструкции `owl-tasks`. Рабочие сессии получают конкретные назначения и меняют только собственные артефакты и worktree; обновления общего учёта передаются координатору.

Это роль существующей основной сессии, а не новый скил верхнего уровня. Несколько сессий не должны самостоятельно одновременно выбирать свободную задачу и перезаписывать ROADMAP. Инструкции не предоставляют атомарного захвата или гарантированной блокировки файла.

Передача роли координатора либо владения задачей выполняется явно. Устаревший исполнитель не должен продолжать запись после передачи. Неизвестное состояние прежней сессии нельзя автоматически считать её завершением. Работа на нескольких компьютерах с общим распределённым владением не входит в MVP.

### 9.2. Готовность среды и интеграция

Подготовка worktree проверяет доступность скилов, правил и папки задачи из рабочей сессии. В OpenCode обнаружение проектных скилов ограничено границей worktree, а доступ к внешней папке может требовать отдельного разрешения.[^opencode-skills][^opencode-agents]

Одновременно используемые порты, базы, временные файлы и другие общие ресурсы разводятся по правилам целевого проекта. Разные ветки не устраняют смысловые конфликты: пересекающиеся контракты заранее согласовываются, тесно связанные изменения при необходимости выполняются последовательно.

Перед интеграцией учитывается актуальная целевая ветка; проверка отдельных веток не заменяет проверку их сочетания. Git-операции не должны затрагивать чужие незакоммиченные изменения. При невозможности безопасной интеграции задача не объявляется `done`.

После принятой интеграции worktree можно удалить штатными средствами Git, предварительно проверив локальные данные. Постановка и отчёты сохраняются. Push, PR, merge и развёртывание выполняются только в пределах согласованной политики; готовность задачи сама по себе не выдаёт новых разрешений.

## 10. Модели и делегирование

Используются уровни `standard` и `advanced`. Схема workflow задаёт требуемый уровень и предпочтительный контекст шага; конфигурация harness связывает их с конкретными профилями и доступными моделями.

Исходные предпочтения пользователя: `standard` — Luna 6, `advanced` — Sol 6. Это пользовательские названия предпочтительных моделей, а не гарантированные идентификаторы провайдера. При настройке должны быть проверены реальные доступные ID; нельзя выдумывать идентификатор или незаметно понижать уровень при недоступности модели.

Начальная политика: основной агент, планирование, сложная диагностика и ревью — `advanced`; реализация достаточно определённой задачи и оформление согласованных документов — `standard` с явной возможностью повышения. Она подлежит проверке на реальных задачах, а не считается универсальным ранжированием сложности.

Основной агент может сам выполнять brief, plan и управление. Реализацию целесообразно держать вместе с тестами и исправлениями в одном рабочем контексте; ревью — в отдельном. Документирование делегируется по необходимости, а не обязательно.

Загрузка скила не должна трактоваться как автоматическое переключение модели. В OpenCode модель связывается с агентом; без отдельного назначения субагент может наследовать модель основного агента.[^opencode-agents] Интеграция должна проверить доступность нужных профилей, рабочую директорию и передачу результатов. Если harness не предоставляет предполагаемой возможности, ограничение сообщается явно.

## 11. Документы, шаблоны и установка

### 11.1. Профиль документации

Правила, спецификации и ADR используют [минимальный профиль OKF, определяемый OWL](../skills/owl-okf/references/okf_profile.md). Проверенная при подготовке документа версия внешней спецификации — OKF 0.2. Она использует Markdown с YAML-frontmatter; `type` обязателен для обычных документов, а для `index.md` предусмотрены отдельные правила оформления.[^okf]

OWL требует удобных индексов и рабочих ссылок для своих сценариев, не приписывая эти более строгие требования внешнему формату. Теги необязательны. Не нужны каталог в облаке, графовая база, автоматические оценки доверия или принудительное преобразование всех рабочих артефактов задач в OKF.

Минимально нужны шаблоны постановки задачи, технического плана, ревью, спецификации, ADR, индекса правил и подключения через `AGENTS.md`. Шаблон `AGENTS.md` должен содержать готовый для включения в существующий файл раздел с порядком выбора правил и передачи контекста. Остальные точные поля уточняются вместе со скилами-потребителями, а не создаются все заранее. Неиспользуемые разделы не заполняются ради формальности.

### 11.2. Установка в целевой проект

README объясняет человеку назначение OWL, текущую готовность и способ установки агентом. Начало установки не должно требовать уже установленного `owl-init`: агент получает материалы OWL и читает инструкцию из них напрямую.

MVP поддерживает один документированный способ проектной установки выбранной версии. Установщик действует по инструкциям, без собственного исполняемого кода. Для нового проекта он создаёт `AGENTS.md` по шаблону подключения; в существующем добавляет недостающие инструкции с учётом уже имеющихся, не заменяя файл целиком и не создавая дубликатов. Существующие правила, документация и конфигурация сохраняются; добавление OWL не означает их полную замену.

Повторный запуск той же версии не создаёт дубликаты и не затирает локальные изменения. Конфликты показываются явно. Необходимые сведения включают используемый harness, соответствие моделей, расположение материалов, команды проверок, способы наблюдения поведения, правила Git и разрешения. Неизвестные значения обозначаются, а не угадываются как проверенные.

Установка не ослабляет существующую безопасность ради успешного запуска. Должна проверяться работа и в основном проекте, и в отдельном worktree. Способ размещения общих справочников и шаблонов не должен оставлять ссылки на недоступную исходную папку разработчика OWL.

Собственный `AGENTS.md` репозитория OWL и шаблон подключения в другой проект — разные материалы.

## 12. Безопасность, знания и совершенствование

Агент использует только разрешённые инструменты и данные. Скилы не служат основанием для доступа к секретам, расширения разрешений, разрушительной очистки или публикации. Запрещается обходить контроль необоснованным отключением тестов и правил либо переписыванием критериев приёмки.

Внешние документы, логи и сообщения рассматриваются как данные, а не как инструкции изменить полномочия. Рабочие отчёты не должны содержать секреты и ненужные персональные данные.

Подтверждённые повторно используемые знания сохраняются в предназначенных документах проекта. Гипотезы отделяются от фактов; повторяющаяся ошибка по возможности устраняется в самом процессе или существующих проверках, а не только добавлением очередной памятки.

`owl-self-review` использует доступные артефакты, историю и результаты, указывает пределы наблюдения и формулирует предложения с основаниями. Улучшения OWL оформляются отдельными задачами, а не незаметными правками установленной копии. Для оценки достаточно сначала наблюдать время до принятого результата, участие человека, переделки и сбои; точные метрики не придумываются при отсутствии данных.

## 13. Критерии готовности MVP

MVP считается готовым после проверки поведения, а не только создания перечисленных файлов. Минимальные сценарии приёмки:

- [ ] Установка и повторная установка в существующий проект сохраняют пользовательские файлы и дают доступ к необходимым инструкциям.
- [ ] Одинаковое содержимое скилов используется в двух проектах с различающимися правилами; агенты выбирают соответствующие правила, а не переносят настройки первого проекта во второй.
- [ ] `owl-brief` оставляет согласованные требования и связанные исполнимые задачи, не начинает реализацию без соответствующего запроса.
- [ ] `/owl` выполняет одну подходящую задачу, связывает результат с требованиями и сохраняет реальные результаты проверок.
- [ ] Пустой, отрицательный или устаревший артефакт не служит основанием для успешного перехода. Проверяется в том числе изменение кода после принятого ревью.
- [ ] Отсутствие обязательного правила, проверки, модели или разрешения не скрывается под сообщением об успехе.
- [ ] Работа продолжается в новой сессии по фактическому состоянию, назначениям и материалам задачи без потери незавершённых изменений.
- [ ] Две независимые задачи выполняются в разных worktree с одним координатором; общий ROADMAP не дублируется, интеграция проводится последовательно.
- [ ] Задача, зависящая от другой, начинается только после доступности принятого результата предшественника; проверяется объединённая версия.
- [ ] Ревью обнаруживает заранее внесённое нарушение требований или применимого правила и не ограничивается формальным одобрением.
- [ ] `owl-fix` различает подтверждённую причину и гипотезу, проверяет исправление либо фиксирует обоснованную остановку.
- [ ] Self-review формирует предложения на основании наблюдений, не выдаёт недоступную историю за изученную и не меняет OWL автоматически.

Проверки могут выполняться существующими инструментами и вручную по сценариям. Создание собственного тестового фреймворка OWL не требуется. Непроверенная возможность явно обозначается как непроверенная.

## 14. Поэтапная разработка OWL

### 14.1. Нулевой этап — основа проекта

Первая сессия создаёт собственную документацию и точку входа OWL, минимальные правила его разработки с работающей навигацией и локальный план последующих задач. Она **не реализует перечисленные скилы, их полноценные шаблоны, команды и конфигурацию моделей**.

В новом репозитории ещё нет работающего OWL и исходной ревизии для обычного цикла worktree. Поэтому подготовка основы выполняется доступными средствами основной сессии с явным указанием этой границы. Нельзя требовать уже работающий `owl-init` для создания самого OWL или выдавать первичную подготовку за проверку будущего workflow. Дальнейшие задачи, изменяющие проект, выполняются в своих worktree после появления пригодной исходной ревизии.

### 14.2. Последующие сессии

Работа разбивается на небольшие задачи с собственными критериями приёмки. Рекомендуемая логика:

1. Проработать общий контракт применения правил и минимальный профиль документов; реализовать `owl-okf`.
2. Добавить `owl-tasks` и необходимые ему шаблоны учёта.
3. Добавить `owl-git` и проверить жизненный цикл worktree.
4. Последовательно проработать `owl-plan`, `owl-implement`, `owl-review` и `owl-document`, добавляя используемые ими шаблоны.
5. Собрать `owl-orchestrator` и минимальные схемы выполнения; проверить одну задачу от постановки до принятого изменения.
6. Добавить `owl-brief` и `owl-fix` как пользовательские входы в общий процесс.
7. Завершить `owl-init`, подключение к OpenCode, профили и пользовательские команды; добавить `owl-self-review`.
8. Проверить переносимость правил, прерывания, отрицательные сценарии и параллельное выполнение задач.

Это порядок внедрения, а не отдельный дублирующий реестр текущих статусов. Актуальные задачи разработки самого OWL находятся в его локальном `tasks/ROADMAP.md`. Каждый скил и шаблон детализируется в своей задаче; большой этап не означает обязательную реализацию всех его частей за одну сессию.

Фактические пути установки, точный синтаксис конфигурации выбранного harness, поля шаблонов и команды Git уточняются в соответствующих задачах по актуальной документации. Для их выбора не нужно заранее строить универсальную систему расширений.
